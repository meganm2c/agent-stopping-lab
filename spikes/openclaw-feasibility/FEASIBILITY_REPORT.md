# OpenClaw feasibility spike

## Decision: YES, WITH CAVEATS

**OpenClaw supports this narrow contract more cleanly than the tested Letta configuration.** One live `diag_001`, budget-2 smoke preserved the exact model snapshot, used the explicitly selected OpenClaw runtime, executed exactly two Python diagnostic tools, blocked a third request, and returned a valid, correct diagnosis. No 20-run study was run.

**This is not full stopping-contract parity.** The tools remained visible after the cap. The wrapper returned a budget-exhaustion observation, and the model voluntarily answered. Microsoft disables tool use after its cap. That difference must be resolved or explicitly treated as a separate stopping implementation before a controlled comparison.

## Live smoke transcript

Scenario: `diag_001`, “API requests are being rejected for all users.” Budget: **2 executed diagnostic calls**. Exactly one live run.

| Attempt | Tool | Component | Executed | Observation |
|---|---|---|---|---|
| 1 | `check_status` | `api` | Yes | API unavailable; configured request limit is zero. Evidence `api_status`. |
| 2 | `check_recent_change` | `api` | Yes | No configuration/deployment change in the incident window. Evidence `api_change`. |
| 3 | `check_status` | `cache` | **No** | `tool_budget_exhausted`: “Return your diagnosis using observed evidence.” No cache observation or evidence ID. |

Final output, validated against the existing `Diagnosis` model:

```json
{
  "predicted_root_cause": "api_configuration_issue",
  "explanation": "The API is rejecting all requests due to a configuration setting where the request limit is set to zero, causing startup validation to fail and making the API unavailable. No recent changes were made, indicating a pre-existing misconfiguration.",
  "evidence_used": ["api_status", "api_change"]
}
```

- Four model calls; each requested at most one tool.
- Tokens: **1,557 input + 123 output = 1,680 total**.
- SDK run duration: **11,615 ms**. This is not whole CLI startup time or comparable performance evidence from a study.
- Last assistant stop reason: **`stop`**; no abort; CLI exit 0.
- Existing deterministic evaluator: diagnosis correct, evidence sufficient, completeness 1.0, no unobserved citations. `api_status` alone met this scenario's required evidence; the extra `api_change` call is scored redundant/excess.
- Native cost metadata reported zero because custom catalog prices were not populated. **Zero is not the actual billed cost.** No cost comparison is made.

See [smoke and evaluation evidence](evidence/smoke.json), [all four HTTP bodies](evidence/requests.json), and [blocked preflight](evidence/preflight.json).

### Finalization finding

The denied third request produced an ordinary tool-result observation. OpenClaw made a fourth model call and accepted a natural JSON final answer. A second explicit user/model-only turn was **not required for this observed run**.

However, all four requests still included all three tools. This does not prove automatic tool removal, guaranteed finalization under repeated blocked requests, or the exact Microsoft budget boundary. The wrapper is authoritative for execution, but the error observation changes the model's trajectory. Future comparison must either add and verify a supported tools-disabled finalization boundary or name this as a distinct budget policy and use matched controls. A turn abort alone would not solve it.

The documented `finalizeSettledTurn` facility concerns terminal recovery after settled tools with no visible assistant text; it is not an automatic budget-counter API. It was not invoked or claimed as this run's finalization mechanism. [Settled finalization contract](https://docs.openclaw.ai/plugins/sdk-agent-harness/sessions-and-results#settled-tool-finalization).

## Tools, context and leakage

`bridge.py` imports the original `DiagnosticEnvironment`, `DiagnosticTools` indirectly through `ToolRecorder`, and the original recorder. It creates one recorder per process and handles requests sequentially over JSON lines. The JavaScript plugin queues all executions on a promise chain; the recorder independently checks executed count before touching the diagnostic environment. It records blocked attempts separately. No scenario behavior was rewritten.

The fixture handed to OpenClaw contains only diagnostic instructions, incident text, tool schemas and the diagnosis schema. No scenario object, ground truth, difficulty, rubric, required-evidence list or historical result is serialized to model context. The diagnosis schema is available to the host but was not submitted as an API `response_format` in this test.

All four captured HTTP bodies show only the three diagnostic schemas. They contain no shell, filesystem, web, memory, session, cron, messaging or MCP tools. The plugin itself spawns the fixed Python bridge as host infrastructure; the model has no general subprocess interface. Workspace files were not injected.

Schema differences remain: OpenClaw sorted tool names, added `additionalProperties: false`, and submitted `strict: true`. It also sent `stream: true`, `stream_options.include_usage`, `store: false`, a prompt-cache key, and `max_completion_tokens: 32768`. These should be explicitly matched or recorded in a future Microsoft comparison.

The supported `before_prompt_build` hook replaces OpenClaw's general assistant system prompt with the original diagnostic instructions. Actual outbound context still adds:

1. A system sentence identifying the current model and how to answer model-identity questions.
2. A timestamp prefix on the incident report.

No workspace paths, host identity, memory contents, skill instructions, project files or previous-run messages remained in the tested outbound context. Native `systemPromptReport` describes pre-hook assembly and still lists excluded material/skill metadata; it should not be treated as the effective model prompt. The captured HTTP body is the evidence. **Prompt equivalence with Microsoft is not claimed.**

## Hook ordering

In the published `openclaw@2026.9.7` source:

- `dist/agent-tools.before-tool-call-C1CeFtM4.mjs`, around line 2944: `await hookRunner.runBeforeToolCall(...)`. This gate can delay/block execution.
- `dist/builtin-openclaw-dCw2mRD9.mjs`, around line 3340: `hookRunnerAfter.runAfterToolCall(...).catch(...)` is called **without await**. The observer is not a safe asynchronous controller barrier.
- The custom tool's `execute` awaits the Python observation before returning its result. A future controller could be awaited inside that serialized wrapper, before the result is returned to OpenClaw. Preventing later execution there is plausible; final-answer behavior after controller STOP still requires its own test.

No adaptive policy/controller was implemented. The observed hook log happened to be ordered, but that does not override the asynchronous source contract. [Official hook reference](https://docs.openclaw.ai/plugins/hooks/reference).

## Phoenix / OpenTelemetry

OpenClaw's separate `diagnostics-otel` plugin supports **OTLP HTTP/protobuf** with configurable trace endpoints. Native spans include `openclaw.run`, `openclaw.harness.run`, `openclaw.model.call`, and `openclaw.tool.execution`. Its schema uses `openclaw.*` and `gen_ai.*`, not automatically the OpenInference attributes used by this project. [Exporter setup](https://docs.openclaw.ai/gateway/opentelemetry/setup), [native spans](https://docs.openclaw.ai/gateway/opentelemetry/spans-and-events).

| Field | Evidence captured here / instrumentation needed |
|---|---|
| Root/run | Native run ID, duration, and model-hook trace context; custom reconstructed CHAIN span. |
| Runtime/model/version | Native `agentHarnessId`, model-call events and terminal receipt; package version added by spike. |
| Tool name/input/output | Native tool hooks plus exact Python wrapper record. |
| Evidence ID, canonical index, executed flag | Custom recorder fields; blocked calls remain distinguishable. |
| Latency | Native run/model duration; Python invocation duration excludes IPC overhead. |
| Tokens | Per-assistant usage checked against native aggregate; each response counted once. |
| Final answer/stop reason | Native last assistant and terminal metadata, validated by host. |

`export_trace.py` generated **eight spans**: one root, four LLM spans, three tool-attempt spans (one blocked). The OTLP protobuf payload was encoded and decoded successfully. OpenInference kind/model/input/output/token attributes are added explicitly. Only LLM child spans carry token-count attributes, so the reconstructed root does not duplicate them.

This is an **offline reconstruction/prototype**, with approximate boundaries derived from recorded event times. It is not the native exporter or a live Phoenix capture. No Phoenix server was started and no ingest/UI rendering test was performed. Protocol compatibility is established by the OTLP encoding; end-to-end Phoenix ingestion remains unverified. See [trace summary](evidence/trace-summary.json) and `evidence/trace.otlp.pb`.
